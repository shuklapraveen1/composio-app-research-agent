What this is

One hundred applications were researched end to end, classified against a fixed taxonomy, and then checked. The headline number is the one that is hardest to flatter: field-level accuracy on Sample B, fifteen applications the improved classifier had never been evaluated against, scored across 11 verified fields against values established by independent verification.

  • 97.6%Field-level accuracy, Sample B
  • 100Applications researched
  • 47 / 35 / 15Buildable / with friction / blocked
  • 49With an MCP server

Two numbers are reported for every sample because one of them alone is misleading. Field-level accuracy asks how many individual values are right. Row-level accuracy asks how many applications are right in every field, and it is always much lower. A pipeline that quotes only the first is hiding the second.

The problem this pipeline solves

Deciding which integrations to build is a research problem before it is an engineering one. The facts that matter - is there an API, how broad is it, can a developer actually get credentials, what stands in the way - are scattered across vendor documentation, pricing pages and repositories, and they are exactly the kind of facts a language model will answer fluently whether or not it knows.

So the pipeline is built around one rule: a value is worth nothing without the evidence behind it. Every field cites the pages it came from, confidence is computed from properties of that evidence rather than declared by the model, and the accuracy claim is measured on a sample the final rules had never seen.

Three ways of not knowing

The taxonomy separates what a single "unknown" would collapse. not_found means the sources did not say. unavailable means they did say, and the answer is that the thing does not exist. unclear means the sources disagree or the question does not resolve to one value. The difference matters: absence of evidence and evidence of absence lead to different decisions.

How the pipeline works

The stages are fixed in order. Research is the only stage that touches all 100 applications; verification touches 30, which is what keeps the cost of checking bounded while still supporting a defensible accuracy claim.

The locked stage sequence.
StageWhat it does
RegistryNormalise the supplied 100 apps into stable ids and categories.
Channel A researchOne pass over all 100 apps, citing sources per field.
Evidence extractionEvery claim becomes an evidence item with a domain, type and the fields it supports.
ClassificationDeterministic rules map observations onto the taxonomy.
ValidationPure checks: cited evidence exists, derived values follow from their inputs.
Trigger reviewRisk-based queue - identity, contradictions, missing critical evidence.
SamplingTwo disjoint stratified samples of 15 apps, seeded from the master seed.
VerificationChannels B, C and D over the samples only.
ReconciliationFixed precedence resolves disagreements; cardinality respected.
AccuracySample A scored against frozen first-pass values; Sample B after the improvement phase.
Analytics and case studyDeterministic metrics, patterns, and this page.

Two judgements that are not left to a model

Confidence is computed

Confidence is a function of recorded properties of the evidence: whether the product was identified, whether the vendor's own documentation was cited, whether every critical field carries evidence, whether anything contradicts anything else, and how many distinct sources were found. A record reaches high only with all of those and at least 3 sources. A single missing critical field, an unresolved identity or a lone source drops it to low regardless of how confident the prose sounded.

Buildability is a decision tree, not an opinion

Three independent legs are answered first - technical feasibility, credential accessibility, commercial accessibility - and the verdict is the worst of them, with a definite failure outranking a gap. That is why a product with an excellent API can still be blocked: the API was never the binding constraint.

Breadth anchors, so the word means the same thing for every app.
API breadthWhat it means
narrowSmall set of resources or capabilities.
moderateMeaningful API coverage but limited to a subset of the product.

very broadExtensive coverage across most major product capabilities.

Verification and what it measured

Verification is only meaningful if the channels can disagree, so Channel B never sees Channel A's answer and does not share its rules, and Channel D is silent unless a reviewer actually ruled on a field. Silence is deliberate: a human rubber-stamping the pipeline's own output would make the accuracy number circular.

The four channels and what each one is for.
ChannelMethodScopeWhat it catches
AResearchAll 100 appsGathers sources and classifies every field.
BIndependent re-derivationSamplesReads the same sources with different rules, without seeing Channel A's answer.
CCitation auditSamplesChecks that each cited page supports the field it is cited for.
DHuman reviewDisputed and triggered fieldsAdjudicates where the automated channels disagree or a trigger fired.

What the first pass got wrong

Sample A was a diagnosis rather than a score. Each failure was traced to the rule that produced it, and the rule was changed once for every application rather than patched per app. The classifier version is recorded on every record, so which rules produced which value is never in doubt.

The improvement phase, v1 to v2.
ChangeFailure modeWhat v2 does insteadSample A misses
api breadth coverage anchorAPI breadth was a count of documented resource groups, so a large reference covering one corner of a product scored very_broad.v2 caps the count-derived breadth by the documented share of the product the API actually covers.1
blocker completenessBlockers were only named when an app was blocked outright, so 'buildable with friction' records were silent about the friction, and unblocked apps read as though nothing had been established.v2 names friction blockers explicitly and records 'none' when the decision tree found nothing in the way.14
credential access plan gatingCredential access was read off the signup tier alone, so a product with a free account but a paid-only API was recorded as self_serve_free.v2 resolves credential access from the plan that actually unlocks the API, together with partner, approval and self-hosting gates, and derives the matching access restrictions rather than copying only those the source spelled out.6
derived restriction provenanceAccess restrictions were cited to the credential page without saying so, so the citation audit read them as claims the page never made.v2 records restrictions as derived from the documented access conditions and says so in the rationale, so the audit judges the citation as support for a conclusion rather than as a quotation.0
event mechanism distinctionAnything event-like was recorded as native_webhooks, which erased the difference between a callback, a gateway stream and polling.v2 keeps the observed event mechanism as the source states it.1

The result: field-level accuracy moved from 86.1% on the first pass to 97.6% on applications the new rules had never been evaluated against.

What the data says

  • MCP status is often unestablished. 50 of 100 applications have no MCP status that the sources could establish either way.
  • Friction is commercial, not technical. 32 of 100 applications are buildable only past a paid plan or an administrator's approval.
  • Vendors publishing their own MCP servers. 32 of 100 applications ship a vendor-published MCP server.
  • Capable APIs behind a human gate. 25 of 100 applications document a broad API that a developer cannot reach without an administrator, a contract or a partner programme.
  • MCP coverage is community-first. 17 of 100 applications are reachable through an MCP server that the vendor did not publish.
  • Event delivery is not always a webhook. 16 of 100 applications deliver change events by streaming, polling, or not at all.

What this does not establish

  • Evidence is cited, not fetched in this run. The committed run replays a reviewed source corpus so that anybody can reproduce it byte for byte without credentials or network access. Every evidence item records retrieval: cited for exactly this reason. A live run would record fetched and carry page excerpts.
  • 5.3% of verified field values are unresolved. That is reported rather than filled in. A confident wrong answer is more expensive than an admitted gap.
  • One reviewer. Channel D is a single human. Inter-rater agreement is not measured, so the reconciled values inherit that reviewer's judgement on the 32 fields they ruled on.
  • The taxonomy has gaps. Self-hosting is friction that no blocker value names, so it is carried as other and flagged. API breadth is a judgement anchored to documented resource groups; reasonable readers disagree, and Sample B's remaining misses are mostly exactly that disagreement.
  • Accuracy is measured on 15 applications per sample. Fifteen apps is enough to locate systematic rule failures and far too few to put a tight confidence interval around the headline number.
  • Findings are a snapshot. Pricing, plans and MCP servers move; the dataset records what the sources said as of 2026-09-16.
